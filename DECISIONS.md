# Практическая работа 9

## Вариант 21

Часть А: StockMovement содержит date типа LocalDate.
Warehouse.receive и issue получают дату через LocalDate.now(clock).
Публичные сигнатуры receive(code, q) и issue(code, q) сохранены.
Часть Б: addMovementsByDate(Warehouse wh, LocalDate date) возвращает операции за дату.
Метод расположен в Warehouse и перебирает movements переданного склада.
Результат содержит иммутабельные записи и является новым ArrayList.

## Решение 1

Формулировка: дата операции определяется через Clock, принадлежащий Warehouse.
Конструктор без аргументов использует Clock.systemDefaultZone().
Конструктор Warehouse(Clock) позволяет передать фиксированные часы.
Альтернатива: вызывать LocalDate.now() напрямую внутри каждой операции.
Обоснование: фиксированные часы делают проверки воспроизводимыми.
Тестам не приходится зависеть от даты запуска или ждать перехода через полночь.
В интерактивном режиме автоматически используется текущая дата компьютера.
Clock проверяется на null при создании Warehouse.
Дата вычисляется один раз для каждой операции.
Задание не требует учёта времени суток, поэтому запись хранит LocalDate.

## Решение 2

Формулировка: каталог хранит собственные копии StockItem.
findByCategory создаёт новый список с копиями изменяемых позиций.
Альтернатива: копировать только список и возвращать исходные StockItem.
Обоснование: поверхностная копия позволила бы вызвать increase вне Warehouse.
В результате остаток изменился бы без записи StockMovement.
Копируются code, name, category и quantity.
StockMovement является record с неизменяемыми компонентами.
Для результата поиска движений достаточно копии списка.
equals и hashCode StockItem используют только неизменяемый code.
Изменение quantity не нарушает нахождение элемента в HashSet.
Ключами items служат String, их сравнение выполняет реализация String.

## Порядок изменения состояния

Сначала проверяется наличие кода.
Затем создаётся StockMovement и проверяются его поля.
StockItem.increase проверяет положительность q и переполнение int.
StockItem.decrease проверяет положительность q и достаточность остатка.
После успешного изменения запись добавляется в movements.
Обычный отказ в проверках не меняет остаток и историю.
Сводка вычисляется заново при запросе totalsByCategory.
Math.addExact обнаруживает переполнение суммы категории.
Приложение рассчитано на последовательное выполнение команд.

## Ответы на контрольные вопросы

### Вопрос 1
Какая проверка защищает от вероятной ошибки входных данных

Проверка допустимости выдачи находится в StockItem.decrease. Метод сначала отвергает неположительное
количество, затем сравнивает запрошенное количество с текущим остатком. Ошибка вероятна при ручном вводе,
когда сотрудник вводит количество из заявки, не сверив его с наличием на складе. Если запрос превышает
остаток, выбрасывается IllegalArgumentException, количество оборудования сохраняется, а Warehouse.issue не
добавляет запись движения. Граница включена: выдача всего остатка допустима и оставляет ноль единиц. Эти
случаи проверяют unit/6, unit/13 и unit/25. Само наличие позиции отдельно проверяется в Warehouse.requireItem
через items.get(code), поэтому неверный инвентарный код также не создаёт движение.

### Вопрос 2
Где размещено ключевое бизнес правило

Ключевое правило состоит в том, что успешная складская операция изменяет остаток и создаёт одну запись истории
с типом, количеством и датой. Оно реализовано в Warehouse.receive и Warehouse.issue, поскольку Warehouse
одновременно владеет каталогом и списком движений. Ограничения самого количества находятся в
StockItem.increase и decrease, где доступны текущий остаток и правила его изменения. Перед изменением
создаётся валидный StockMovement, затем вызывается метод позиции, и только после его успешного завершения
запись добавляется в историю. Благодаря такому порядку обычные ошибки входных данных не оставляют частично
выполненной операции. SelfCheck проверяет согласованность остатка и числа движений при успехе и отказе.

### Вопрос 3
Как Activity диаграмма отражает код

Блок поиска позиции на Activity-диаграмме соответствует вызову requireItem из Warehouse.receive и issue.
Внутри requireItem выполняется items.get(code), а отсутствие результата приводит к IllegalArgumentException и
завершает ветку ошибки. Далее диаграмма показывает получение даты через LocalDate.now(clock) и создание
StockMovement. Ромб проверки количества отражает валидацию записи движения, а ветви прихода и выдачи
соответствуют вызовам increase и decrease. Если изменение успешно, управление приходит к общему блоку
добавления записи в movements. Сводка пересчитывается по запросу totalsByCategory. Для выдачи 100 единиц из
остатка 12 путь заканчивается на проверке достаточности, до изменения остатка и журнала.

### Вопрос 4
Какое изменение затронет минимум классов

Изменение правила выбора даты операции затронет один класс Warehouse. Например, вместо календарной даты
компьютера можно потребовать дату в часовом поясе Europe/Moscow. Достаточно изменить создание Clock в
конструкторе без аргументов, сохранив получение даты через LocalDate.now(clock) в операциях. StockItem не
работает с датами, а StockMovement уже хранит LocalDate, поэтому их структура остаётся подходящей.
Передаваемый через второй конструктор Clock позволяет проверить границу суток без изменения системных часов. В
SelfCheck обновляются только ожидания тех сценариев, которые зависят от выбранного пояса. Бизнес-операции,
формат поля date и метод поиска движений за день сохраняют свой контракт.

## Фрагмент кода для анализа

Линейный поиск по List последовательно сравнивает коды и в худшем случае просматривает весь каталог, хотя в
этой модели уже предусмотрен Map<String, StockItem>, предназначенный для обращения к позиции по её
инвентарному коду. При росте каталога такой перебор требует O(n) сравнений на каждую операцию, тогда как
HashMap.get(code) обычно выполняет поиск за ожидаемое O(1), при этом для строкового ключа используются equals
и hashCode класса String. Исправленный подход состоит в вызове StockItem item = items.get(code) с последующей
проверкой item == null и выбрасыванием IllegalArgumentException, если код отсутствует. Такое решение
соответствует проверке существования кода R9, поддерживает правило уникальности R1 и оставляет Map закрытым
полем склада в соответствии с R6, поскольку наружу передаётся результат операции, а не изменяемая внутренняя
коллекция.

Исправление в Warehouse.requireItem: items.get(code), проверка null, возврат item.
